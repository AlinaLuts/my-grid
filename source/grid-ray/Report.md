## Завдання 4. Аналіз «болю Гріда»

### 1. Несумісності оточення (Windows, Linux, WSL)

Під час налаштування я зіткнулася з трьома рівнями несумісностей:
1) **Windows vs Linux** — Ray не має офіційних wheels для Python 3.13/3.14 на Windows, тому довелося використати WSL Ubuntu.
2) **WSL networking** — за замовчуванням WSL має NAT-мережу (172.x.x.x), яка не бачить інші ноути; довелося увімкнути `networkingMode=mirrored` у `.wslconfig`.
3)  **Версії Python** — Head мав Python 3.12.3, Worker 3.12.14; Ray відмовився з'єднувати кластер, доки версії не вирівнялися.

### 2. Накладні витрати серіалізації чанка

Під час передачі чанка через мережевий сокет виникають:
1) **Серіалізація** — `topology_dict` (118 вузлів + 186 ліній) перетворюється в байти через pickle/cloudpickle.
2) **Мережевий overhead** — TCP-пакети, підтвердження, повторні передачі.
3) **Десеріалізація** — Worker розпаковує байти назад у Python-об'єкти.
4) **Плазмове сховище Ray** — додатковий шар кешування, який сповільнює на localhost.

### 3. Повільний вузол у пулі

Якщо один вузол у 2-3 рази повільніший, **всі інші чекають на нього**. Це **закон Густафсона-Барсіса**: при гетерогенності час виконання визначається **найповільнішим вузлом**. У моєму випадку це проявилося як зниження throughput з 10 964 (pool) до 5 577 (ray).

### 4. Чому немає прав адміністратора — проблема

Класичний Grid вимагає **двостороннього зв'язку** між вузлами:
- Windows Firewall з профілем Public блокує **вхідні з'єднання** за замовчуванням
- Без прав адміністратора не можна відкрити порти (6379, 20000-30000)
- Роутер ізолює Wi-Fi та Ethernet (client isolation) — вузли не бачать один одного
- Це **непереборна** перешкода: без мережевої зв'язності кластер не працює

### 5. Чому HTTP/SOCKS проксі не працює для Ray

Ray використовує **не HTTP**, а **gRPC** з **динамічними портами** (20000-30000). HTTP-проксі працює тільки з портом 80/443, а SOCKS — з обмеженим набором протоколів. Ray потребує **прямого доступу** до GCS та Raylet-портів.
